# AI Agent 语义层生成系统 - 方案文档

## 1. 项目目标

构建一个自动化系统，能够分析代码仓库并生成高质量的语义层文档（Markdown 格式），使 AI Agent 能够：
- 深入理解代码仓库的业务语义
- 准确把握代码的执行行为和副作用
- 获得任务相关的精准上下文
- 最终实现 90% 以上的代码生成准确率

## 2. 核心设计理念

### 2.1 借鉴 Palantir Ontology 的三层架构

```
┌─────────────────────────────────────────┐
│         AI Agent (读取语义层)            │
├─────────────────────────────────────────┤
│      Semantic Layer (Markdown 文档)     │
│  ┌──────────┬──────────┬──────────┐    │
│  │ 语义层   │ 行为层   │ 上下文层 │    │
│  └──────────┴──────────┴──────────┘    │
├─────────────────────────────────────────┤
│    语义层生成器 (Python 系统)           │
│  ┌──────────────────────────────────┐  │
│  │ GitNexus 集成 / AST 分析         │  │
│  │ LLM 语义推断                     │  │
│  │ 模式识别                         │  │
│  └──────────────────────────────────┘  │
├─────────────────────────────────────────┤
│         代码仓库                        │
└─────────────────────────────────────────┘
```

### 2.2 与传统方案的区别

| 维度 | 传统 RAG | 本方案 |
|------|---------|--------|
| 信息组织 | 代码片段 + 向量检索 | 结构化语义层 |
| 业务理解 | 无 | 业务域 + 职责描述 |
| 行为理解 | 无 | 执行流程 + 副作用 |
| 上下文质量 | 依赖检索质量 | 预计算 + 精准匹配 |
| Agent 准确率 | 60-70% | 目标 90%+ |

## 3. 语义层结构设计

### 3.1 Semantic Layer（语义层）

**目标**：让 Agent 理解"代码是什么"

**内容**：
```markdown
## 业务域划分
- Auth（认证授权）
  - 职责：用户身份验证、权限管理
  - 核心实体：User, Role, Permission
  - 关键流程：登录、注册、权限检查

## 代码实体语义
### Function: validateUser
- 语义角色：Validator
- 业务域：Auth
- 职责：验证用户凭证的有效性
- 输入：用户名、密码
- 输出：验证结果（布尔值）
- 置信度：0.95
```

### 3.2 Behavioral Layer（行为层）

**目标**：让 Agent 理解"代码做什么"

**内容**：
```markdown
## 执行模式
### API_ENDPOINT: POST /api/login
- 入口点：handleLogin (src/api/auth.ts:45)
- 执行流程：
  1. validateUser() - 验证凭证
  2. createSession() - 创建会话
  3. generateToken() - 生成 JWT
- 副作用：
  - DB_WRITE: sessions 表
  - CACHE_WRITE: Redis session
- 风险级别：HIGH

## 影响分析
### 修改 validateUser 的影响
- 直接影响（深度1）：
  - handleLogin (90% 置信度)
  - handleRegister (85% 置信度)
- 间接影响（深度2）：
  - authRouter (导入依赖)
- 风险评估：HIGH - 影响所有认证流程
```

### 3.3 Contextual Layer（上下文层）

**目标**：为 Agent 提供任务相关的精准上下文

**内容**：
```markdown
## 编码约束
### 命名规范
- 函数：驼峰命名，动词开头（validateUser, createSession）
- 类：帕斯卡命名（UserService, AuthController）
- 常量：全大写下划线（MAX_LOGIN_ATTEMPTS）

### 架构模式
- 分层架构：Controller → Service → Repository
- 依赖注入：使用构造函数注入
- 错误处理：统一使用 Result<T, Error> 模式

## 代码示例
### 添加新的验证器
参考：validateUser (src/auth/validate.ts:15)
```typescript
export function validateEmail(email: string): boolean {
  // 1. 参数验证
  if (!email) return false;

  // 2. 格式检查
  const emailRegex = /^[^\s@]+@[^\s@]+\.[^\s@]+$/;
  return emailRegex.test(email);
}
```
```

## 4. 技术实现方案

### 4.1 系统架构

```
输入：代码仓库路径
  ↓
GitNexus 分析（可选）
  ↓
AST 解析 + 静态分析
  ↓
语义推断（LLM）
  ↓
模式识别
  ↓
Markdown 生成
  ↓
输出：语义层文档
```

### 4.2 核心模块

#### 4.2.1 代码分析器（Analyzer）
- **功能**：解析代码结构
- **技术**：
  - 优先使用 GitNexus（如果可用）
  - 备选：tree-sitter 直接解析
- **输出**：符号表、调用图、聚类信息

#### 4.2.2 语义推断器（Semantic Enricher）
- **功能**：为代码添加业务语义
- **技术**：
  - LLM API（OpenAI/Anthropic）
  - 基于代码结构和命名的规则推断
- **输出**：语义角色、业务域、职责描述

#### 4.2.3 行为分析器（Behavior Analyzer）
- **功能**：识别执行模式和副作用
- **技术**：
  - 静态分析（数据库调用、API 调用）
  - 模式匹配（装饰器、路由定义）
- **输出**：执行流程、副作用列表

#### 4.2.4 上下文提取器（Context Extractor）
- **功能**：提取编码规范和示例
- **技术**：
  - 代码风格分析
  - 相似代码聚类
- **输出**：约束规则、代码示例

#### 4.2.5 Markdown 生成器（MD Generator）
- **功能**：生成结构化的语义层文档
- **技术**：
  - 模板引擎
  - 分层组织
- **输出**：SEMANTIC_LAYER.md

### 4.3 数据流

```python
# 1. 分析阶段
repo_path → Analyzer → {
    symbols: List[Symbol],
    calls: List[Call],
    clusters: List[Cluster]
}

# 2. 语义推断阶段
symbols + clusters → SemanticEnricher → {
    entities: List[SemanticEntity],
    domains: List[BusinessDomain]
}

# 3. 行为分析阶段
calls + symbols → BehaviorAnalyzer → {
    patterns: List[ExecutionPattern],
    side_effects: List[SideEffect]
}

# 4. 上下文提取阶段
symbols + patterns → ContextExtractor → {
    constraints: List[Constraint],
    examples: List[CodeExample]
}

# 5. 生成阶段
all_data → MDGenerator → SEMANTIC_LAYER.md
```

## 5. 质量保证机制

### 5.1 语义准确度保证

1. **置信度评分**：每个语义推断都有置信度分数
2. **多源验证**：结合命名、结构、注释多方面信息
3. **人工校准**：低置信度项目可人工标注
4. **持续学习**：从 Agent 使用反馈中改进

### 5.2 完整性保证

1. **依赖完整性检查**：确保所有依赖关系都被记录
2. **覆盖率统计**：统计语义覆盖的代码比例
3. **缺失项报告**：明确标注未能分析的部分

### 5.3 可维护性保证

1. **增量更新**：支持只更新变更部分
2. **版本管理**：语义层文档版本化
3. **变更追踪**：记录语义层的变更历史

## 6. 使用流程

### 6.1 生成语义层

```bash
# 分析代码仓库并生成语义层
python src/main.py analyze /path/to/repo

# 输出：F:/semantic_layer_project/output/SEMANTIC_LAYER.md
```

### 6.2 Agent 使用语义层

```python
# Agent 读取语义层
with open("SEMANTIC_LAYER.md") as f:
    semantic_layer = f.read()

# 将语义层作为系统提示词
system_prompt = f"""
你是一个代码助手。以下是代码仓库的语义层：

{semantic_layer}

请基于这个语义层理解代码并生成准确的代码。
"""
```

### 6.3 更新语义层

```bash
# 增量更新（只分析变更的文件）
python src/main.py update /path/to/repo

# 强制全量重新生成
python src/main.py analyze /path/to/repo --force
```

## 10. 风险与应对

### 10.1 风险

1. **LLM 推断不准确**
   - 应对：多源验证 + 置信度评分 + 人工校准

2. **大型仓库性能问题**
   - 应对：增量分析 + 并行处理 + 缓存机制

3. **语言支持不全**
   - 应对：优先支持主流语言，逐步扩展

4. **Agent 不按语义层执行**
   - 应对：优化文档结构，提供使用指南

### 10.2 降级方案

如果 LLM 不可用：
- 使用基于规则的语义推断
- 降低语义丰富度，保证基础功能

如果 GitNexus 不可用：
- 使用 tree-sitter 直接解析
- 简化调用图分析
